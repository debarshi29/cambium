# ADR 0001: Base control-loop architecture

## Status
Accepted (resolves the OPEN DECISION flagged in CLAUDE.md §2).

## Context
CLAUDE.md fixes the control-loop *architecture* and varies only the tools
and prompts populating its nodes. That requires picking one architecture
before any generation code is written. The spec's intent was to inherit the
winning variant from the separate `loop-engineering` project; that project's
run artifacts are not available in this environment, so the choice below is
made on documented first-principles reasoning about what this project needs
from a loop, not by re-deriving `loop-engineering`'s empirical result. If
`loop-engineering`'s artifacts become available later, this ADR should be
revisited and either confirmed or superseded — don't treat the choice below
as equivalent to having checked.

## Decision
The base loop is a **plan → act → verify → reflect** loop with an explicit
skill-extraction step on novel success:

1. **Plan** (`planner` prompt node): given a task, decide a retrieval query
   over the skill library (which categories/signatures to look for).
2. **Act**: attempt the task — via a retrieved skill, a base capability, or
   (if neither exists) a generation candidate.
3. **Verify**: run the attempt in the sandbox against the task's cases.
4. **Reflect** (`reflector` prompt node): on failure, decide whether to
   retry generation, fall back, or give up, bounded by a retry budget.
5. **Extract** (`critic` prompt node): on a *novel* success (i.e. no
   existing skill covered this signature), decide whether the winning
   source is worth proposing as a skill candidate for the admission gate.

This is a hybrid of a pure reflection loop and a pure plan-execute loop, not
either in isolation. It was chosen over the two extremes for two reasons
specific to this project:

- A **pure plan-execute loop** (plan once, execute, done) has nowhere to
  hang a `reflector` prompt node — reflection is exactly the mechanism this
  project needs a node for, since prompt-node coverage across planner /
  reflector / critic is what the tools-vs-prompts attribution ablation
  (CLAUDE.md §4) needs to probe.
- A **pure reflection loop** (retry indefinitely against unstructured
  feedback) has no natural admission-gate boundary — "verify" as a distinct,
  sandboxed step is what makes skill/prompt admission decidable at all
  (CLAUDE.md §3.2/§3.4 condition 1).

## Consequences
- Three prompt nodes exist to evolve: `planner`, `reflector`, `critic`. Node
  count is fixed by this decision, not chosen later per-experiment — adding
  a fourth node would itself be a loop-architecture change, out of scope per
  CLAUDE.md §7.
- The loop's node graph and routing are held constant for the rest of the
  project, as CLAUDE.md §2 requires. Only what is generated by each node's
  active prompt, and which skills the "act" step retrieves, are allowed to
  vary across generations.
